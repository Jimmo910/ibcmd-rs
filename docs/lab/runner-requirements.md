# ТЗ: лаборатория паритета на self-hosted runner GitHub Actions

**Исполнитель:** агент (Claude Code, Codex или другой), запущенный владельцем на его
лабораторном компьютере (Windows, SQL Server, установленные платформы 1С,
тестовые базы). Работа идёт в checkout `Untru/ibcmd-rs`.

**Зачем.** Агенты на других машинах (например, на VPS) должны прогонять паритет
выгрузки ibcmd-rs с нативным `ibcmd` на больших конфигурациях: ERP УХ, УТ, ДО,
Бухгалтерия, БСП, ServiceDesk. Им не нужен доступ к этой машине: они запускают
`gh workflow run lab-parity.yml …` и читают сводку прогона. Всё выполняется в
отдельной виртуальной машине, только заранее описанными шагами и только над
копиями баз.

Прочитай `AGENTS.md` и `CONTRIBUTING.md` репозитория до начала работы.
Изменения в репозитории оформляются PR по их правилам.

Этот документ — предложение устройства лаборатории. Его слияние не означает,
что ВМ или runner уже созданы, и не подтверждает паритет #521. Допуск конкретной
ревизии к корпусам, результаты прогонов и оставшиеся исходниковые/fixture-блокеры
приёмки фиксируются отдельно.

## Результат (критерии приёмки)

1. Контроллер `ibcmd-lab` на Hyper-V и изолированный offline исполнитель из
   раздела 2. Платформы и копии баз находятся у исполнителя; у контроллера нет
   корпусов. Для чистых окружений сохранены контрольные точки `os-clean` и `runner-ready`.
2. Runner `ibcmd-lab-1` зарегистрирован в выбранной в разделе 5 защищённой области с метками
   `self-hosted, windows, x64, ibcmd-lab`. Он работает службой под учётной записью
   без прав администратора и стартует вместе с ВМ.
3. До регистрации runner-а выбран и проверен механизм допуска только доверенного
   управляющего workflow (раздел 5). Если платформа репозитория не позволяет
   ограничить его доступ, приватные корпуса не подключаются к runner-у публичного
   репозитория; владелец выбирает закрытый управляющий репозиторий.
4. Через PR добавлены управляющий `lab-parity.yml`, скрипт в `tools/lab/`,
   проверки границ допуска и `docs/lab/README.md`. Конкретное место workflow
   определяется выбранным механизмом; установка ВМ этим PR не выполняется.
5. Прогоны разрешённых владельцем точных SHA `master` и кандидата #521 завершены,
   их сводки содержат коды возврата и все классы различий. Базовая линия привязана
   к неизменяемым копиям баз, точным сборкам платформ, языку и версиям инструментов.
   Различия не превращаются в PASS из-за ожидаемого количества. Флаг
   `allow_incomplete_v2` разрешён только для отдельно помеченного диагностического
   прогона; он не закрывает строгую native-приёмку. Публикация сводки — отдельный
   доверенный шаг после проверки безопасного формата.
6. Итоговый отчёт владельцу (см. последний раздел).

## Что согласовать с владельцем до действий

Спрашивай и жди ответа перед каждым из этих пунктов:

- включение Hyper-V и любая перезагрузка хоста;
- ресурсы ВМ: ядра, память, диски. Предложи цифры по итогам инвентаризации;
- редакция и лицензия Windows в ВМ. Windows Server Evaluation на 180 дней
  подходит для лаборатории;
- путь к дистрибутивам платформ 1С и SQL Server. С портала 1С ничего не скачивай:
  нужны учётные данные владельца;
- какие базы разворачивать и откуда брать копии: `.bak`, `.dt`, `.cf`;
- регистрация runner-а (нужен токен с правами администратора репозитория) и
  изменение настроек репозитория;
- любой пароль или учётные данные.

## Чего не делать никогда

- Не подключаться к рабочим базам и не писать ни в одну базу, кроме копий,
  созданных для лаборатории.
- Не давать ВМ доступ к общим папкам и сетевым ресурсам хоста, кроме
  одноразового копирования дистрибутивов и бэкапов, согласованного с владельцем.
  Входящие порты не открывать.
- Не класть секреты в репозиторий, в логи и в параметры workflow.
- Лабораторный workflow запускается только через `workflow_dispatch`.
  Одна эта настройка не ограничивает другие workflows: runner с метками
  `self-hosted,windows,x64,ibcmd-lab` подходит и заданию с
  `runs-on: [self-hosted, windows, x64]`. Проверка упоминания `ibcmd-lab`
  не является контролем доступа; обязательна граница из раздела 5.
- Не собирать и не запускать произвольный `ref` до допуска точного SHA владельцем.
  `cargo build` выполняет код сборки из проверяемой ревизии; ВМ с приватными
  копиями баз и постоянным кешем не делает такой код безопасным.
- Не выгружать в артефакты и комментарии деревья выгрузки, XML, BSL и тела
  модулей. Артефакты публичного репозитория доступны всем.
- Не давать учётной записи runner-а права администратора ни в ВМ, ни на хосте.

## Шаги

### 1. Инвентаризация хоста (только чтение)

Выясни и сообщи владельцу:
- редакцию Windows и доступность Hyper-V;
- число ядер, объём памяти, свободное место на дисках;
- установленные версии платформ 1С, где лежат дистрибутивы;
- версию SQL Server и список тестовых баз с размерами;
- где лежат лабораторные корпуса (`E:\ibcmd_lab`, `D:\temp` и т.п.).

Предложи план: ресурсы ВМ, список баз, способ их доставки в ВМ.

Нужные версии платформ берутся из списка баз. Сейчас в проекте встречаются
8.3.27.2214, 8.5.1.1150 и 8.5.1.1529.

### 2. Виртуальная машина

- Hyper-V, поколение 2. Default Switch/NAT разрешён только для bootstrap без
  приватных корпусов: получение допущенных исходников, закреплённых зависимостей
  и инструментов. Он не ограничивает исходящую передачу данных кандидатом.
- Сборка кандидата и baseline исполняет их код. Она идёт без корпусов в окружении,
  отделённом от доверенного контроллера; сетевые загрузки заканчиваются до неё,
  сборка использует подготовленные зависимости offline.
- Доступ к корпусам получает только изолированный offline исполнитель, например
  отдельная ВМ с SQL Server внутри. У него нет внешней сети, DNS и доступа к хосту
  или узлам GitHub/Actions, учётных данных runner-а и общих каталогов контроллера.
  Границу задаёт владелец снаружи исполнителя; кандидат не может её снять.
  Служба Actions с её сетевым каналом остаётся в окружении контроллера без корпусов.
- Кандидатные stdout/stderr, файлы и Actions workflow commands остаются на закрытом
  диске исполнителя: их нельзя транслировать в job log, кеш или артефакт даже после
  окончания прогона. Только отдельный доверенный collector передаёт publisher-у
  проверенную сводку из раздела 6. Исполнитель с данными/остаточным состоянием
  не подключается обратно к сети; повторное использование требует чистого образа.
  Пока изоляция и этот канал вывода не проверены на синтетических данных,
  приватные корпуса не подключаются.
- Каналы ingress/egress задаёт владелец вне исполнителя. На ingress используется
  одноразовый носитель/образ только для чтения без общего каталога и сети. До
  подключения корпуса доверенный launcher проверяет подпись владельца и JSON Schema
  manifest-а из закреплённого контроллера: run id, точные candidate/baseline SHA,
  feature set, разрешённые относительные имена и SHA-256 каждого входного файла.
  Принимаются только manifest, допущенные бинарники и перечисленные профили/параметры;
  неизвестные поля/файлы, ссылки, выход за корень, превышение лимитов и несовпадение
  хеша блокируют прогон. Кандидат не меняет manifest, launcher или ключ проверки.
- Egress — отдельный носитель закрытого отчёта, отключаемый от исполнителя до
  чтения доверенным изолированным collector-ом; обратного канала к контроллеру нет.
  Отчёт считается недоверенным: collector ограничивает размер, проверяет run id,
  SHA и схему, не исполняет вложения/команды и не передаёт сырые файлы publisher-у.
  Только сформированная им сводка по закрытой публичной схеме раздела 6 проходит
  повторную проверку publisher-а. Конкретные носители, ACL, схемы и лимиты фиксируются
  владельцем в manifest до первого корпуса; неподтверждённый канал — блокер.
- Кандидат и нативный oracle у исполнителя запускаются под отдельной выделенной
  учётной записью ОС без членства в Administrators и без прав управления службами,
  изоляцией и чужими процессами. Ей доступны только чтение допущенного снимка и
  собственные закрытые каталоги результата/временных файлов. Администраторские
  учётные данные и окружение подготовки не наследуются; launcher проверяет
  фактический токен каждого процесса до доступа к корпусу.
- Ориентир по ресурсам: 8 vCPU или половина ядер хоста, 24–32 ГБ памяти,
  системный диск 128 ГБ. Отдельный диск данных `D:` на 300–500 ГБ, размер зависит от
  баз. Выгрузка ERP УХ — около 140 тыс. файлов на дерево, а на базу хранятся
  нативное дерево и деревья прогонов.
- Windows Server 2022/2025 (или согласованная редакция), обновления.
- Контрольная точка `os-clean`.

### 3. Окружения лаборатории

Инструменты сборки готовятся без корпусов; SQL Server, платформы и снимки для
прогона размещаются у offline исполнителя, как требует раздел 2.

- Git, PowerShell 7, Python 3.12, Node.js 22 LTS (нужен для OpenSpec в
  `cargo xtask ci`).
- Visual Studio Build Tools с нагрузкой «Разработка классических приложений на
  C++». Без неё Rust под MSVC не собирается.
- Rust через rustup. Версию задаёт `rust-toolchain.toml` репозитория (1.95.0), rustup
  поставит её сам.
- Платформы 1С нужных версий, вместе с серверными компонентами (`ibcmd`), а также
  `sqlcmd` и `bcp`: их проверяет протокол паритета.
- SQL Server 2022 Developer.
- Проверь, что нативный `ibcmd infobase config export` работает в ВМ на одной
  базе. Если мешает лицензия или защита платформы, остановись и сообщи владельцу.
  Запасной вариант согласуется с владельцем и сохраняет изоляцию раздела 2;
  перенос кандидата с корпусами в online окружение хоста не допускается.

### 4. Тестовые базы

- Восстанови копии из бэкапов или создай нативным `ibcmd` из `.dt`/`.cf`, на версии
  платформы, с которой база должна выгружаться.
- Для каждого SQL-прогона доверенный администратор готовит свежий database
  snapshot лабораторной копии. Оба сравниваемых SHA читают один и тот же снимок.
  Подстановка доступной для записи восстановленной базы вместо него запрещена.
- У службы контроллера `ghrunner` нет доступа к базам. Offline исполнитель
  использует отдельную учётную запись, встроенную аутентификацию и только минимальные
  права чтения нужного снимка. Для обеих учётных записей запрещены `db_owner`, владение базой,
  `sysadmin` и права управления снимками, схемой либо данными. Административная
  подготовка выполняется другой учётной записью без передачи её учётных данных job-у.
- Снимок наследует права исходной копии в момент создания; изменить их внутри
  снимка нельзя. Администратор подготавливает минимальные права до создания,
  затем закрывает исполнителю доступ к исходной копии и остальным базам.
  Перед запуском под фактической учётной записью исполнителя сначала проверяются
  точные server/database, ожидаемые `database_id`, `create_date`,
  `source_database_id` и `is_read_only=1` снимка. Администратор записывает эти
  значения сразу после создания в защищённый manifest данного run id; имя
  снимка или id исходной базы сами по себе его не идентифицируют. Сверка с manifest
  обязательна перед каждым из двух SHA-прогонов и после них; пересоздание, смена
  endpoint или несовпадение любого значения блокирует результат и использование кеша.
  Только после подтверждения endpoint проверяются чтение, отказ DML/DDL на
  заранее подготовленном тестовом объекте и отказ подключения к исходной копии.
  Ошибка блокирует прогон; отпечаток после работы не заменяет запрет записи до неё.
  Несовместимость нативной выгрузки с этим режимом — блокер, а не повод выдать права записи.
  [Свойства и наследование прав database snapshots](https://learn.microsoft.com/en-us/sql/relational-databases/databases/database-snapshots-sql-server),
  [поля идентичности и времени создания sys.databases](https://learn.microsoft.com/en-us/sql/relational-databases/system-catalog-views/sys-databases-transact-sql).
- Для `dbms: file` администратор готовит свежую копию и предъявляет её исполнителю
  как read-only/immutable mount, сохраняя оригинал отдельно. До открытия `1Cv8.1CD`
  launcher под фактической непривилегированной учётной записью проверяет canonical
  path, отсутствие ссылок/выхода за допущенный корень и запрет записи по правам.
  Недеструктивная проба открытия существующего файла на запись без изменения байтов
  и проба создания нового служебного файла в каталоге должны отказать. Успех любой
  пробы останавливает прогон; пробный файл удаляет администратор до подготовки
  новой read-only копии. Одна метка «immutable» либо файловый ReadOnly-атрибут
  запрет не доказывает. SHA-256/размер и идентичность mount-а сверяются с защищённым
  manifest до каждого SHA и после прогона; результат при изменении недействителен.
  Запись oracle/candidate идёт в отдельный рабочий каталог; если oracle требует
  изменения самой базы, это блокер данного режима, а не разрешение снять защиту.
- Конфиг лаборатории `D:\ibcmd-lab\lab.json` лежит вне репозитория. Это список баз:
  - `id`: `bsp-8327`, `erp-uh-8327`, `erp-uh-85`, `ut-115`, `do-30`, `acc-30-85`, `sd-310-85`…;
  - название;
  - `dbms` (`MSSQLServer` или `file`);
  - сервер и имя фактически используемого снимка, его исходная копия,
    `database_id`, `create_date`, `source_database_id` и run id защищённого manifest,
    либо canonical `db_path`, идентичность mount-а и хеш свежей read-only файловой копии;
  - версия платформы и путь к её `ibcmd`;
  - версия формата XML.
- Если для какой-то базы нужен пароль, он хранится в окружении offline исполнителя,
  а в закрытом `lab.json` указывается только имя этой переменной. Служба Actions
  и публичный workflow пароль не получают. Launcher формирует явный allowlist
  окружения вместо наследования parent environment: сборка и процессы, которым
  пароль не нужен, его не получают. Процессу, который сам подключается к БД,
  передаётся только credential минимально привилегированной read-only snapshot
  identity из раздела 4, никогда пароль администратора/исходной базы; значение
  не попадает в аргументы, manifest, отчёт или лог. Проверка запуска подтверждает
  фильтрацию окружения на синтетическом секрете до подключения корпуса.
  [CreateProcessW: lpEnvironment](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw#parameters).

### 5. Допуск и runner

До регистрации выбери с владельцем один из реально доступных вариантов:

- runner group с политикой доступа только для выбранного управляющего workflow,
  если аккаунт и тариф это поддерживают. Обычный workflow закрепляется в allowlist
  за защищённой веткой, reusable workflow — за полным SHA; сами исполняемые
  зависимости закреплены, как указано ниже. Доступ проверяется отрицательным
  тестом другого workflow;
- отдельный закрытый управляющий репозиторий только для доверенных операторов,
  к которому относится runner. Его доверенный manual workflow получает ревизии
  публичного `Untru/ibcmd-rs` только после допуска владельцем.

Нельзя обещать workflow allowlist для repository-level runner-а без такой
возможности. Если ни один вариант не доступен, регистрацию остановить и описать
ограничение; защита на уровне меток не заменяет этот выбор.
[Маршрутизация по меткам](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/use-in-a-workflow)
и [доступ через runner groups](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/manage-access)
описаны в документации GitHub.

Управляющий workflow и скрипт берутся только из доверенного закреплённого
источника, а не из `ref` кандидата. Все исполняемые зависимости
проверяются до работы с кешами, сборки и подключения корпусов: каждый action
(включая checkout, setup и publisher), reusable workflow и внешний скрипт
закреплён за полным проверенным commit SHA из проверенного upstream репозитория;
транзитивные/composite actions проверяются так же. Ссылки на теги/ветки и скачивание
исполняемого скрипта по изменяемому URL запрещены. Для контейнеров нужен image
SHA-256 digest, для runner/toolchain/загружаемых бинарников — точная версия и
проверенный SHA-256; всё входит в manifest. Локальные скрипты контроллера входят
в закреплённый SHA контроллера, кандидат их не подменяет.
[Закрепление workflow dependencies](https://docs.github.com/en/actions/reference/security/secure-use#using-third-party-actions).

До запуска контроллер обязан:

1. Разрешить `ref` и `baseline_ref` в полные SHA разрешённого репозитория, записать
   их в закрытый manifest и получить допуск именно этих SHA. Новая вершина ветки
   требует нового допуска; имя PR/ветки и успешный публичный CI его не заменяют.
2. Проверить разрешённые `bases` по внешнему lab.json и наличие безопасного корня
   прогона. Ошибка не должна запускать сборку или открывать базы.
3. Проверить, что режим запуска соответствует реально настроенной политике
   workflow/repository access. В неподдерживаемой конфигурации отказать.

Не исполнять скрипт `tools/lab` из кандидата как управляющий код. После допуска
продукт собирается из зафиксированного SHA в изолированном окружении раздела 2;
результат не устанавливается вместо доверенных инструментов. Рабочие каталоги и
кеши разных уровней доверия не смешиваются. После нарушения границы допуска прежний кеш и
состояние ВМ не используются как доверенная основа следующего прогона.

- Допущенная точная версия `actions-runner` для win-x64 с проверенным SHA-256
  в `D:\actions-runner`; обновление проходит тот же допуск зависимостей.
  Автообновление без этого допуска запрещено.
- Регистрация только в выбранной защищённой области: имя `ibcmd-lab-1`, метки
  `self-hosted,windows,x64,ibcmd-lab`. Токен даёт владелец, или ты получаешь его
  через `gh api` с его разрешения. Служба контроллера не получает приватные
  корпуса; после проверки допуска они доступны только offline исполнителю.
- Служба под `ghrunner` без прав администратора, автозапуск.
- Постоянные каталоги, чтобы сборки не начинались с нуля: `CARGO_HOME`, `RUSTUP_HOME`
  и `CARGO_TARGET_DIR` в `D:\ibcmd-lab\cache`; рабочий каталог `D:\actions-runner\_work`.
  Кандидатные target и данные прогона изолированы от кеша контроллера и не
  копируются в него обратно после доступа к корпусам.
- Контрольная точка `runner-ready`.

### 6. Изменения в репозитории (PR)

**`.github/workflows/lab-parity.yml`:**
- `on: workflow_dispatch`, и больше ничего. Входы:
  - `ref` — ветка или коммит, по умолчанию `master`;
  - `bases` — `all` или список id через запятую;
  - `baseline_ref` — с чем сравнивать, по умолчанию `master`; пусто — без сравнения;
  - `allow_incomplete_v2` — boolean, по умолчанию `false`. Пробрасывается как
    `IBCMD_RS_ALLOW_INCOMPLETE_V2_FORMS=1`.
- Selector соответствует выбранной в разделе 5 границе. Для runner group
  задаются одновременно её фактическое допущенное имя и метки:

  ```yaml
  runs-on:
    group: <approved-runner-group>
    labels: [self-hosted, windows, x64, ibcmd-lab]
  ```

  Для repository-level runner-а, зарегистрированного только в закрытом управляющем
  репозитории, используется отдельный selector в этом же репозитории:

  ```yaml
  runs-on: [self-hosted, windows, x64, ibcmd-lab]
  ```

  Это альтернативы, не fallback при недоступности группы. Если закрытый контроллер
  тоже использует group, обязателен первый вариант с её именем. Guard проверяет
  выбранную пару group/labels и repository binding, а не только custom label.
  GitHub требует совпадения обеих частей [group + labels](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/use-in-a-workflow#using-labels-and-groups-to-route-jobs).
- `concurrency: lab-parity` без отмены идущего прогона, разумный `timeout-minutes`.
- На лабораторном job только необходимые права чтения; права записи комментариев
  ему не выдаются. `checkout` не сохраняет Git credentials в рабочем дереве.
  Публикация выполняется отдельным доверенным job после проверки сводки,
  без запуска кода кандидата и доступа к корпусам.

**Скрипт прогона в `tools/lab/`** (PowerShell 7 или Python). Для каждой базы:
- **Сборка.** Только после допуска из раздела 5, без корпусов: для каждого
  закреплённого SHA кандидата и baseline отдельный release oracle binary через
  `cargo build --locked --offline --release --no-default-features --features platform-oracle`.
  Его отдельный `--target-dir` привязан к SHA и feature set; бинарник, SHA-256
  и flags записываются в manifest. Это сборка для `docs/parity-protocol.md`:
  перед запуском проверяется наличие `dump-sources` и всех остальных команд,
  которые требует `scripts/export-ibcmd-vs-ours.ps1`.
  Product-only сборка с `--no-default-features` без oracle допустима отдельно
  только для шагов, не выполняющих protocol export; она не заменяет oracle binary
  и не перезаписывает его target/artifact.
- **Нативная выгрузка.** Для SQL используется только проверенный свежий snapshot
  из раздела 4; endpoint нативного и кандидатного процессов должен совпадать с ним.
  Ключ кеша
  содержит идентификатор снимка, точную сборку платформы, формат, язык, параметры
  команды и отпечатки всех читаемых состояний. Одного `CONFIG` недостаточно:
  `CONFIGSAVE` и расширения `CONFIGCAS`/`CONFIGCASSAVE` могут менять результат при
  прежнем `CONFIG`. Если полнота ключа не доказана, кеш отключён. У нативного
  запуска отдельный рабочий `--data` согласно протоколу.
- **Наша выгрузка** тем же синтаксисом, что у нативного `ibcmd`, плюс `--platform`
  для SQL Server.
- **Сравнение побайтово по SHA-256:** файлов у нативного и у нас, совпало,
  различается, только у нативного, только у нас. Код возврата и устойчивая
  категория ошибки; исходный stderr сохраняется только в закрытом отчёте.
  Относительно закреплённого SHA baseline: сколько файлов
  исправлено и сколько сломано.
- **Готовые наработки:** существующий `tools/rea/matrix_parity.py`, если нужен,
  проходит ревью и закрепляется в SHA контроллера, как любой управляющий скрипт.
  Протокол `docs/parity-protocol.md` и `scripts/export-ibcmd-vs-ours.ps1` —
  эталон того, как выгружать, ничего не меняя в базе; его семантику не
  дублируй и не ослабляй. Прогон только читает базы.
- Деревья выгрузок старше последних N прогонов удаляются только по manifest-у
  принадлежащих прогону каталогов после проверки абсолютного корня. Базы,
  исходные бэкапы и неизменяемая baseline не участвуют в этой очистке.

**Вывод:**
- Лабораторный процесс формирует закрытый машинный отчёт. Доверенный publisher
  принимает только фиксированную схему: согласованный публичный id базы, полные
  SHA, версии, целочисленные счётчики/коды возврата, хеши деревьев и категорию
  ошибки из закрытого перечисления. Неизвестное поле или неверный тип — отказ
  публикации. Данные не подставляются в shell-команду.
- Только такая сводка попадает в `GITHUB_STEP_SUMMARY` и, если разрешено,
  комментарием в нужный PR. Не копировать туда stdout/stderr сборки или продукта,
  первую строку исключения, произвольный Markdown/JSON либо названия объектов.
- Относительные пути XML могут раскрывать прикладные имена так же, как абсолютные.
  Списки путей, XML/BSL, тела модулей, учётные данные и необработанные ошибки
  остаются закрытыми. Диагностическая публикация путей требует отдельной
  минимизации и допуска владельца; по умолчанию её нет.
- Полные отчёты и списки остаются в ВМ: `D:\ibcmd-lab\reports\<run-id>\`.
  Перед публичной публикацией проверка на синтетическом отчёте с путями,
  фрагментом BSL и тестовым секретом должна отказать, не выводя их в лог.

**Проверка в CI** (шаг Quality или `cargo xtask ci`):
- в публичном репозитории запретить все способы выбора лабораторного runner-а
  вне разрешённого управляющего workflow: общие метки `self-hosted`/OS/архитектуры,
  custom labels, groups и динамические `runs-on`. Непроверяемое выражение
  отказать, а не считать безопасным;
- у управляющего workflow нет триггера, кроме `workflow_dispatch`;
- негативный пример `runs-on: [self-hosted, windows, x64]` в другом workflow
  отвергается, хотя `ibcmd-lab` в нём отсутствует;
- проверки отказа SHA/base admission и незакреплённой исполняемой зависимости
  выполняются до сборки и подключения корпуса; group-вариант без нужного group
  отвергается. Проверки публичной схемы не пропускают сырые диагностические данные.

Этот guard — проверка конфигурации в дополнение к реально настроенной политике
runner-а; он не заменяет запрет исполнения изменённого workflow со стороны GitHub.

**`docs/lab/README.md`:**
- как устроена лаборатория, список баз (только id и версии);
- как добавить базу, обновить платформу и откатить ВМ к контрольной точке;
- базовая линия master: таблица первого прогона.

### 7. Настройки репозитория (делает владелец или ты с его разрешения)

- Настроить выбранную в разделе 5 границу доступа и проверить её отрицательным
  сценарием до подключения приватных корпусов. Доступность workflow allowlist
  проверить для фактического аккаунта/тарифа; не считать её настроенной по меткам.
- Settings → Actions → General → Fork pull request workflows: «Require approval for
  all external contributors» — дополнительная мера, а не замена workflow isolation.
- Проверить все runner selectors, включая общие метки и expressions. Если runner
  зарегистрирован в закрытом управляющем репозитории, публичные PR не получают
  прямой маршрут к нему.

### 8. Проверка

- До приватных корпусов на синтетических данных проверить отсутствие исходящей
  связи у кандидата (включая GitHub), невозможность снять внешнюю границу и утечь
  через stdout/stderr, job commands, кеш или артефакты. Сырой вывод и после
  завершения остаётся закрытым; publisher получает только проверенную сводку.
- На синтетическом ingress/egress проверить отказ неверной подписи, хеша, run id,
  неизвестного поля/файла и вывода вне схемы; корпусы до этого не подключать.
- Проверить токены ОС candidate/oracle (оба non-admin), фильтрацию окружения,
  отказ writable file mount и подмены/пересоздания SQL snapshot между двумя SHA.
- Под фактической учётной записью проверить идентификаторы и режим только чтения SQL-снимка,
  отказ DML/DDL и подключения к исходной копии по разделу 4; отказ любой проверки
  блокирует прогон. Сохранить закрытые протоколы проверок без SQL-текстов с данными.
- Для каждого oracle binary проверить feature set и полный protocol command
  preflight; product-only binary должен быть отвергнут до обращения к базе.
- Сначала проверить отказ неподтверждённого SHA, неизвестной базы и запрещённого
  runner selector без монтирования корпусов и запуска сборки.
- Прогон закреплённого master по всем базам: записать базовую линию для точных
  снимков/профилей. Исторические цифры README не заменяют текущую native-сверку;
  различия классифицировать и сообщить владельцу.
- Для кандидата #521 разрешить точный SHA ветки `feat/rea-export-parity`, затем
  выполнить строгий прогон относительно закреплённого master. При необходимости
  отдельный запуск `allow_incomplete_v2=true` записать как диагностику с явным
  режимом, не как native PASS.
- В итоговой таблице отдельно успех команды и результат паритета. Только полное
  требуемое сравнение без неразобранных потерь даёт основание закрывать приёмку;
  известное количество отличий либо совпадение с master не доказывает совпадение
  с нативным выводом. Неподготовленные raw/private fixtures и семейные profile
  blockers #521 не закрываются установкой runner-а.

Публикуется только проверенная безопасная сводка; размещение комментария в #521
не означает одобрения или слияния его исходников.

## Как этим будут пользоваться агенты

`<trusted-controller-repository>` — выбранный в разделе 5 репозиторий
доверенного управляющего workflow. При варианте с закрытым контроллером это
его имя, а не публичный репозиторий с исходниками кандидата.

```text
gh workflow run lab-parity.yml --repo <trusted-controller-repository> \
  -f ref=<ветка> -f bases=erp-uh-85,ut-115 -f baseline_ref=master
gh run list --repo <trusted-controller-repository> --workflow lab-parity.yml --limit 1
gh run watch <run-id> --repo <trusted-controller-repository>
gh run view <run-id> --repo <trusted-controller-repository> --log
```

Ориентир по времени: нативная выгрузка ERP УХ занимает 6–7 минут, наша —
около 3 минут на базу, плюс сборка (из кеша несколько минут).
