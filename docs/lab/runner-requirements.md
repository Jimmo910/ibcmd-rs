# ТЗ: лаборатория паритета на self-hosted runner GitHub Actions

**Исполнитель:** агент (Claude Code, Codex или другой), запущенный владельцем на его
лабораторном компьютере (Windows, SQL Server, установленные платформы 1С,
тестовые базы). Работа идёт в checkout `Untru/ibcmd-rs`.

**Зачем.** Агенты на других машинах (например, на VPS) должны прогонять паритет
выгрузки ibcmd-rs с нативным `ibcmd` на больших конфигурациях: ERP УХ, УТ, ДО,
Бухгалтерия, БСП, ServiceDesk. Им не нужен доступ к этой машине: они запускают
`gh workflow run lab-parity.yml …` и читают сводку прогона. Всё выполняется в
отдельной виртуальной машине, только заранее описанными шагами и только над
копиями баз.

Прочитай `AGENTS.md` и `CONTRIBUTING.md` репозитория до начала работы.
Изменения в репозитории оформляются PR по их правилам.

## Результат (критерии приёмки)

1. Виртуальная машина `ibcmd-lab` на Hyper-V. В ней установлено окружение,
   развёрнуты копии тестовых баз, сделаны контрольные точки `os-clean` и
   `runner-ready`.
2. Runner `ibcmd-lab-1` зарегистрирован в репозитории `Untru/ibcmd-rs` с метками
   `self-hosted, windows, x64, ibcmd-lab`. Он работает службой под учётной записью
   без прав администратора и стартует вместе с ВМ.
3. В репозитории через PR добавлены:
   - `.github/workflows/lab-parity.yml`;
   - скрипт прогона в `tools/lab/`;
   - проверка в CI, что метку `ibcmd-lab` использует только этот workflow;
   - `docs/lab/README.md`.
4. Прогон `gh workflow run lab-parity.yml -f ref=master -f bases=all
   -f baseline_ref=` проходит. Его сводка записана в `docs/lab/README.md` как базовая
   линия master. По README проекта для БСП и ERP УХ ожидается 0 расхождений с
   нативной выгрузкой. Если это не так, не исправляй код, а сообщи владельцу.
5. Прогон ветки `feat/rea-export-parity` с `baseline_ref=master` и
   `allow_incomplete_v2=true` проходит, его сводка опубликована комментарием в PR #521.
6. Итоговый отчёт владельцу (см. последний раздел).

## Что согласовать с владельцем до действий

Спрашивай и жди ответа перед каждым из этих пунктов:

- включение Hyper-V и любая перезагрузка хоста;
- ресурсы ВМ: ядра, память, диски. Предложи цифры по итогам инвентаризации;
- редакция и лицензия Windows в ВМ. Windows Server Evaluation на 180 дней
  подходит для лаборатории;
- путь к дистрибутивам платформ 1С и SQL Server. С портала 1С ничего не скачивай:
  нужны учётные данные владельца;
- какие базы разворачивать и откуда брать копии: `.bak`, `.dt`, `.cf`;
- регистрация runner-а (нужен токен с правами администратора репозитория) и
  изменение настроек репозитория;
- любой пароль или учётные данные.

## Чего не делать никогда

- Не подключаться к рабочим базам и не писать ни в одну базу, кроме копий,
  созданных для лаборатории.
- Не давать ВМ доступ к общим папкам и сетевым ресурсам хоста, кроме
  одноразового копирования дистрибутивов и бэкапов, согласованного с владельцем.
  Входящие порты не открывать.
- Не класть секреты в репозиторий, в логи и в параметры workflow.
- Не запускать workflow на `pull_request`, `pull_request_target`, `push`
  или `schedule`. Только `workflow_dispatch`: репозиторий публичный, и иначе чужой
  PR сможет выполнить код на этой машине.
- Не выгружать в артефакты и комментарии деревья выгрузки, XML, BSL и тела
  модулей. Артефакты публичного репозитория доступны всем.
- Не давать учётной записи runner-а права администратора ни в ВМ, ни на хосте.

## Шаги

### 1. Инвентаризация хоста (только чтение)

Выясни и сообщи владельцу:
- редакцию Windows и доступность Hyper-V;
- число ядер, объём памяти, свободное место на дисках;
- установленные версии платформ 1С, где лежат дистрибутивы;
- версию SQL Server и список тестовых баз с размерами;
- где лежат лабораторные корпуса (`E:\ibcmd_lab`, `D:\temp` и т.п.).

Предложи план: ресурсы ВМ, список баз, способ их доставки в ВМ.

Нужные версии платформ берутся из списка баз. Сейчас в проекте встречаются
8.3.27.2214, 8.5.1.1150 и 8.5.1.1529.

### 2. Виртуальная машина

- Hyper-V, поколение 2, сеть через Default Switch (NAT, только исходящий доступ).
- Ориентир по ресурсам: 8 vCPU или половина ядер хоста, 24–32 ГБ памяти,
  системный диск 128 ГБ. Отдельный диск данных `D:` на 300–500 ГБ, размер зависит от
  баз. Выгрузка ERP УХ — около 140 тыс. файлов на дерево, а на базу хранятся
  нативное дерево и деревья прогонов.
- Windows Server 2022/2025 (или согласованная редакция), обновления.
- Контрольная точка `os-clean`.

### 3. Окружение в ВМ

- Git, PowerShell 7, Python 3.12, Node.js 22 LTS (нужен для OpenSpec в
  `cargo xtask ci`).
- Visual Studio Build Tools с нагрузкой «Разработка классических приложений на
  C++». Без неё Rust под MSVC не собирается.
- Rust через rustup. Версию задаёт `rust-toolchain.toml` репозитория (1.95.0), rustup
  поставит её сам.
- Платформы 1С нужных версий, вместе с серверными компонентами (`ibcmd`), а также
  `sqlcmd` и `bcp`: их проверяет протокол паритета.
- SQL Server 2022 Developer.
- Проверь, что нативный `ibcmd infobase config export` работает в ВМ на одной
  базе. Если мешает лицензия или защита платформы, остановись и сообщи владельцу.
  Запасной вариант — runner на хосте под отдельной учётной записью, только с его
  согласия.

### 4. Тестовые базы

- Восстанови копии из бэкапов или создай нативным `ibcmd` из `.dt`/`.cf`, на версии
  платформы, с которой база должна выгружаться.
- Доступ к SQL Server — встроенной аутентификацией учётной записи runner-а
  (`ghrunner`). Права `db_owner` только на лабораторные копии, на остальное ничего.
  Паролей при этом нет.
- Конфиг лаборатории `D:\ibcmd-lab\lab.json` лежит вне репозитория. Это список баз:
  - `id`: `bsp-8327`, `erp-uh-8327`, `erp-uh-85`, `ut-115`, `do-30`, `acc-30-85`, `sd-310-85`…;
  - название;
  - `dbms` (`MSSQLServer` или `file`);
  - сервер и имя базы либо `db_path`;
  - версия платформы и путь к её `ibcmd`;
  - версия формата XML.
- Если для какой-то базы нужен пароль, он хранится в переменной окружения
  учётной записи runner-а, а в `lab.json` указывается только имя этой переменной.

### 5. Runner

- Последний `actions-runner` для win-x64 в `D:\actions-runner`.
- Регистрация в `Untru/ibcmd-rs`: имя `ibcmd-lab-1`, метки `self-hosted,windows,x64,ibcmd-lab`.
  Токен даёт владелец, или ты получаешь его через `gh api` с его разрешения.
- Служба под `ghrunner` без прав администратора, автозапуск.
- Постоянные каталоги, чтобы сборки не начинались с нуля: `CARGO_HOME`, `RUSTUP_HOME`
  и `CARGO_TARGET_DIR` в `D:\ibcmd-lab\cache`; рабочий каталог `D:\actions-runner\_work`.
- Контрольная точка `runner-ready`.

### 6. Изменения в репозитории (PR)

**`.github/workflows/lab-parity.yml`:**
- `on: workflow_dispatch`, и больше ничего. Входы:
  - `ref` — ветка или коммит, по умолчанию `master`;
  - `bases` — `all` или список id через запятую;
  - `baseline_ref` — с чем сравнивать, по умолчанию `master`; пусто — без сравнения;
  - `allow_incomplete_v2` — boolean, по умолчанию `false`. Пробрасывается как
    `IBCMD_RS_ALLOW_INCOMPLETE_V2_FORMS=1`.
- `runs-on: [self-hosted, ibcmd-lab]`, `concurrency: lab-parity` без отмены
  идущего прогона, разумный `timeout-minutes`.
- `permissions`: `contents: read`, `pull-requests: write` (для комментария).

**Скрипт прогона в `tools/lab/`** (PowerShell 7 или Python). Для каждой базы:
- **Сборка.** ibcmd-rs для `ref` и, если задан, для `baseline_ref`:
  `cargo build --locked --profile iter --no-default-features` (маршрут продукта,
  без платформенного оракула).
- **Нативная выгрузка.** Кешируется по ключу «база + версия платформы + отпечаток
  таблицы `Config`», повторно выгружается только при смене ключа.
- **Наша выгрузка** тем же синтаксисом, что у нативного `ibcmd`, плюс `--platform`
  для SQL Server.
- **Сравнение побайтово по SHA-256:** файлов у нативного и у нас, совпало,
  различается, только у нативного, только у нас. Код возврата и первая строка
  ошибки, если выгрузка упала. Относительно `baseline_ref`: сколько файлов
  исправлено и сколько сломано.
- **Готовые наработки:** если в master уже есть `tools/rea/matrix_parity.py`, бери
  его. Протокол `docs/parity-protocol.md` и `scripts/export-ibcmd-vs-ours.ps1` —
  эталон того, как выгружать, ничего не меняя в базе; его семантику не
  дублируй и не ослабляй. Прогон только читает базы.
- Деревья выгрузок старше последних N прогонов удаляются, чтобы не кончилось место.

**Вывод:**
- В `GITHUB_STEP_SUMMARY` — таблица по базам. Если `ref` — ветка открытого PR,
  та же таблица уходит комментарием в PR.
- В публичный вывод можно: счётчики, хеши деревьев, версии, до 20
  относительных путей различающихся файлов на базу.
- Нельзя: содержимое XML/BSL, абсолютные пути хоста, учётные данные.
- Полные отчёты и списки остаются в ВМ: `D:\ibcmd-lab\reports\<run-id>\`.

**Проверка в CI** (шаг Quality или `cargo xtask ci`). Падает, если:
- метку `ibcmd-lab` упоминает другой workflow;
- у `lab-parity.yml` есть триггер, кроме `workflow_dispatch`.

**`docs/lab/README.md`:**
- как устроена лаборатория, список баз (только id и версии);
- как добавить базу, обновить платформу и откатить ВМ к контрольной точке;
- базовая линия master: таблица первого прогона.

### 7. Настройки репозитория (делает владелец или ты с его разрешения)

- Settings → Actions → General → Fork pull request workflows: «Require approval for
  all external contributors».
- Убедиться, что runner виден в Settings → Actions → Runners и что ни один другой
  workflow не нацелен на `ibcmd-lab`.

### 8. Проверка

- Прогон master по всем базам: записать базовую линию. БСП и ERP УХ — ожидается 0
  расхождений. Сравни с README; расхождение не исправляй, а сообщи.
- Прогон `feat/rea-export-parity`:
  `-f ref=feat/rea-export-parity -f baseline_ref=master -f allow_incomplete_v2=true`.
  Ожидания из PR #521:
  - на ERP УХ, УТ, ДО и БСП ветка не отличается от master;
  - Бухгалтерия 3.0 — около 643 расхождений;
  - ServiceDesk 3.10.28 — 1961 из 1961.

  Сводка уходит комментарием в PR #521.

## Как этим будут пользоваться агенты

```text
gh workflow run lab-parity.yml --repo Untru/ibcmd-rs \
  -f ref=<ветка> -f bases=erp-uh-85,ut-115 -f baseline_ref=master
gh run list --repo Untru/ibcmd-rs --workflow lab-parity.yml --limit 1
gh run watch <run-id> --repo Untru/ibcmd-rs
gh run view <run-id> --repo Untru/ibcmd-rs --log
```

Ориентир по времени: нативная выгрузка ERP УХ занимает 6–7 минут, наша —
около 3 минут на базу, плюс сборка (из кеша несколько минут).
