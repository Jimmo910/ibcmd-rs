# Как брать задачи без Collaboration

Любой участник GitHub, который может комментировать публичные issues, может
взять свободную задачу из [Project №9](https://github.com/users/Untru/projects/9).
Право записи в репозиторий и право редактировать Project для этого не нужны.
Код отправляется через fork и pull request.

| Комментарий в issue | Кто может отправить | Результат |
| --- | --- | --- |
| `/claim` | Участник на свободной Ready issue | Assignees = автор, Status = In progress |
| `/review #123` | Единственный назначенный исполнитель | Свой открытый non-Draft PR #123 в master; Status = In review |
| `/unclaim` | Единственный назначенный исполнитель | Снятие своего назначения; Status = Ready |

Для `/review` принимается также полная ссылка на PR этого репозитория. PR
должен явно ссылаться на issue: `Refs #536` или её полная ссылка. Напишите
одну команду отдельным новым комментарием; редактирование старого комментария
не запускает обработку. Чужую задачу перехватить нельзя. Закрытые,
заблокированные и архивные карточки не обрабатываются; в Backlog сначала
нужна сортировка сопровождающим. Done, закрытие issues, merge и права доступа
команды не меняют. `/review` двигает карточку; `@codex review` в PR отдельно
запускает проверку Codex.

Бот сохраняет в Agent одну строку `Claim bot:` с исполнителем, номером PR и
идентичностью команды. Остальные строки сохраняются. Начинайте работу только
после итогового подтверждения бота и проверки назначения на странице issue.
Pending означает, что результата ещё нет.

## Однократное включение владельцем

1. Влить workflow и код в `master` через обычные проверки. GitHub запускает
   `issue_comment` из основной ветки; PR с кодом ещё не включает бота.
2. От имени владельца Project создать отдельный **classic personal access
   token** с разрешением **project**, ограниченным сроком и без `repo`,
   `workflow`, `admin` и других ненужных scopes. Для этого публичного
   репозитория Project-запросам не нужен приватный repo scope.
3. В [Actions secrets репозитория](https://github.com/Untru/ibcmd-rs/settings/secrets/actions)
   добавить repository secret **PROJECT_TOKEN**. Значение вводится только
   туда: не в issue, чат, коммит, лог или переменную Actions. Не переносить
   личный токен из `gh auth token`.
4. В Actions вручную запустить **Issue self-service**, только для master.
   Job **Project configuration (read only)** проверяет схему Project и право
   обновления, ничего не назначая. Ручной запуск разрешён владельцу.
5. На отдельной тестовой issue в Project/Ready проверить `/claim`,
   `/review #PR` со своим подходящим PR и `/unclaim`. Сверить ответы,
   Assignees, Status и сохранность чужих Agent-строк. Для проверки именно
   внешнего участника команду должен отправить аккаунт без Collaboration.
   Пока этого нет, не утверждать, что живая внешняя проверка пройдена.

Project №9 должен оставаться открытым, с полями Status (single select:
Ready, In progress, In review) и Agent (text). Задачи в Project добавляет и
сортирует сопровождающий. При смене проекта нужна отдельная настройка кода.
Обновляйте secret до истечения срока токена. Отключение: удалить secret или
выключить workflow; уже существующие назначения сохранятся.

`PROJECT_TOKEN` используется только для фиксированных запросов Project
GraphQL. Назначения и ответы выполняет временный `GITHUB_TOKEN` с
`issues: write`; постоянный токен не передаётся PR-проверкам. Комментарии
читаются как данные: бот не исполняет их и не получает код из веток PR.

## Повторы, очередь и сбои

Каждая issue имеет отдельную очередь команд; одновременно обрабатывается
одна команда. [GitHub допускает до 100 ожидающих запусков](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency).
При переполнении запуск может быть отменён: без подтверждения не начинайте
работу, дождитесь освобождения очереди и отправьте новую команду. Первое
успешное назначение побеждает; порядок появления комментариев не обещает
порядок исполнения.

Бот сначала сохраняет квитанцию, затем меняет состояние. Повторный запуск
старого workflow ничего не назначает, даже после `/unclaim`. При ошибке,
отмене или зависшей pending-квитанции проверьте текущее назначение и отправьте
**новый комментарий**. Команда на старом комментарии не восстанавливает
состояние и не заменяет новую команду.

GitHub не даёт общей транзакции для Assignees и полей Project. При отказе
API или вмешательстве другого редактора возможна частичная запись. Бот
останавливается без подтверждения успеха. Текущий исполнитель может новой
`/claim` довести своё назначение до In progress либо `/unclaim` освободить
его. Если появился другой исполнитель или повреждена запись Agent, нужна
сверка сопровождающего; бот чужую запись не очищает. При заполненном Agent
бот отказывает до назначения, не обрезая чужие строки.

## Локальные проверки

```text
python tests/scripts/test_issue_claim_bot.py
cargo xtask check
cargo xtask ci
```

Тесты не используют сеть и секреты: проверяются полный цикл, отказы,
подмена/редактирование комментария, гонки, повторные и запоздавшие команды,
частичные отказы API, привязка токенов и чтение настроек без записи.

[Почему нужен отдельный Project-токен](https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/automating-projects-using-actions):
встроенный `GITHUB_TOKEN` не имеет доступа к Projects. Публичная видимость
Project даёт просмотр; команды посредника позволяют обойтись без выдачи
участникам права прямого редактирования.
